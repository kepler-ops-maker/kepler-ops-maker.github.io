pstack deep research

조사일 2026-09-27 · 웹 검색 14회 + 원문 fetch 12건 · X 원문은 직접 접근이 막혀 threadnavigator/vuink 미러와 인용 보도로 교차 검증함

한 줄 결론: pstack은 Cursor 엔지니어 Lauren Tan(@poteto, React core team)이 사내에서 쓰던 에이전트 스킬 스택을 오픈소스로 푼 것임. "코드를 더 많이"가 아니라 "더 적게, 더 검증되게"가 목표이고, 진입점 하나(/poteto-mode)만 외우면 됨. 다만 풀 워크플로는 빌드 시간이 약 2배라는 실측 비판도 있어서, 작은 작업엔 과잉임.

1. pstack이 뭔가

cursor/plugins - pstack (공식 리포)

Cursor 공식 플러그인. 워크플로 스킬 23~24개 + 엔지니어링 원칙 21개 + 태스크 플레이북 22개 + 전용 서브에이전트 2개(poteto-agent, Comment Sicko) + 자동화 팩(Benny, dormant)으로 구성됨. MIT 라이선스. SKILL.md 표준 포맷이라 Claude Code/Codex에서도 로드 가능하나 /add-plugin, 모델 역할 배정, /loop 등 일부는 Cursor 전용임.

Cursor 마켓플레이스 - pstack

설치는 Cursor 채팅에서 /add-plugin pstack 한 줄임. 부모 리포 cursor/plugins는 스타 약 6.6천 개(2026-09 기준, 서드파티 집계).

제작자: Lauren Tan (@poteto)

Meta, Netflix, Cursor에서 수백만 줄 규모 코드베이스를 다뤘고 React core team에서 React Compiler를 만듦. 최근엔 Grok @Bot 코드베이스의 "gardener"로 pstack을 전면 적용했다고 본인 가이드에서 밝힘.

2. 왜 유행인가 (배경)

  • 사내 검증 후 공개: 2026-05-27 본인이 "내 Cursor 스킬이 지난주 사내 엔지니어링 팀에서 1만 회 사용됐다"며 오픈소스화를 발표함(LinkedIn). 내부 실전 스택이라는 내러티브가 초기 확산의 핵심이었음. 제작자 주장 수치임.
  • "AI slop" 반감의 시기: README 스스로 "AI가 슬롭 코드를 너무 많이 쓴다"는 공감대에서 출발함. 스루풋보다 검증을 앞세우는 포지셔닝이 시니어 개발자층에 먹힘.
  • 제작자 신뢰도: React core team 이력 + "pstack으로 월 2,000 PR을 프로덕션에 냈다"는 본인 가이드 주장. 역시 제작자 주장이며 독립 검증 없음.
  • 인플루언서 리뷰 연쇄: Theo(t3.gg)가 2026-08-19 일주일 실사용 리뷰에서 Matt Pocock 스킬과 비교하며 "자기 워크플로엔 pstack이 arguably better" 평가. Flavio Copes 딥다이브(08-21), Rob Shocks 리뷰(09-08)가 이어짐.
  • 본인 콘텐츠 연재: "Complete Guide to pstack" X 아티클 시리즈(Pt.1 09-01 검증, Pt.2 계획/설계)로 화제성 유지.
  • skills 포맷의 대세화: SKILL.md가 Claude Code, Codex 등에서 공통 포맷이 되면서 "마크다운 스킬 컬렉션" 자체가 2026년 하반기 유행 카테고리임(Matt Pocock 스킬, Superpowers, addyosmani/agent-skills 등).
  • 포트 생태계: pstack-claude(비공식 Claude Code/Codex/OpenCode 포트) 같은 미러가 나오면서 Cursor 외 사용자에게도 퍼짐.

3. 작동 방식과 구체적 사용법

설치와 설정

/add-plugin pstack      # Cursor 채팅에서 설치
/setup-pstack           # 역할별 모델 감지·배정 (~/.cursor/rules/pstack-models.mdc 생성)
/poteto-mode <목표 + 완료 조건>   # 이후엔 이것만 쓰면 됨

기본 모델 배정: 판단·문장·정밀 지정 코드는 Fable 5.1, 빠른 기계적 코드는 Grok, 리뷰 패널은 Fable/Sol/Grok/Opus 혼합. /setup-pstack으로 역할별 변경 가능(auto/inherit-parent는 부모 채팅 모델 상속이라는 뜻이며 모델명이 아님).

프롬프트 작성법 (가이드 핵심)

/poteto-mode export가 재시도 중간에 중복 행을 씀. 먼저 재현하고, 수정하고, 검증해.
/poteto-mode 자고 올게. CI가 flake해도 스택을 머지까지 완료해. 아침까지.
  • 스킬 이름을 나열하지 말고 목표 + 검증 가능한 완료 조건 + 유지해야 할 기존 동작만 적음. 라우팅은 /poteto-mode가 함.
  • 실행 시: 원칙 인덱스 읽기 → 매칭된 플레이북의 단계를 투두에 그대로 verbatim 복사 → 단계별로 필요한 스킬(/how, /architect, /tdd, /interrogate 등) 호출 → 실물 검증. 스킵한 단계는 "skip: 사유"로 남김(조용한 생략 금지).
  • sticky mode라 한번 들어가면 후속 턴에도 유지됨. 주제 바꿀 땐 "new task"라고 말함. Cursor /loop과 결합해 야간 자율 실행 가능.

주요 스킬 직접 호출

  • /how 서브시스템 동작 추적 설명 / /why git·이슈·Slack·Sentry·분석 등 7개 증거 카테고리에서 "왜 이렇게 됐나" 조사 / /teach 두 개를 합쳐 이해시켜줌 / /recall 과거 채팅 기록에서 내 컨텍스트 복원
  • /architect 호출부 사용 예부터 타입·시그니처 설계(구현 중 마찰 증거가 나오면 설계 폐기) / /arena 같은 브리프를 여러 모델이 경쟁 구현 후 최선을 graft / /swarm 슬라이스 분할 병렬 + 통합 리포트 / /interrogate 여러 모델이 diff를 교차 공격(기각한 항목과 사유도 공개)
  • /create-verification-skill 레포에 "검증 능력"을 스킬로 생성(실행→구동→증거 캡처→정리 + feature map) / /maintain-verification-skill 드리프트 감지 / /tdd / /unslop AI 문체 제거 / /bro 직역 해설 / /show-me-your-work TSV 결정 로그 / /automate-me 내 작업 방식으로 나만의 -mode 스킬 생성

Cursor 없이 쓰기

SKILL.md 파일이라 Claude Code/Codex에 폴더 복사로 로드 가능. 비공식 포트 michael-denyer/pstack-claude가 Cursor 전용 요소를 변환해 제공함. 단 /add-plugin, /setup-pstack의 모델 규칙 파일, 서브에이전트별 모델 지정, /loop은 Cursor 전용이라 빠짐.

5. pstack의 차별점 (Matt Pocock 스킬 대비)

  1. 라우터 + sticky mode: /poteto-mode 하나가 플레이북을 골라 단계를 복사하고 스킬을 순서대로 호출함. Pocock 쪽은 사용자가 스킬을 직접 고르는 철학(disable-model-invocation 다수)임.
  2. 멀티모델이 설계의 일부: arena의 경쟁 구현, interrogate의 교차 심사, 역할별 모델 배정이 기본값. Pocock 스킬은 모델 중립이라 이런 구조가 없음.
  3. 검증을 레포의 능력으로 만듦: /create-verification-skill이 실제 앱을 구동하는 CLI+feature map을 생성. Pocock의 TDD/디버깅 루프보다 한 단계 위의 인프라 접근임.
  4. 장기 자율 실행: autonomous-run, orchestrate, autopilot-full/stack, session-pickup, pause-safely, TSV 결정 로그 등 "자고 있는 동안" 워크플로가 완비됨. Pocock 쪽은 handoff 정도.
  5. 조사 스킬의 깊이: /why가 Slack·Sentry·이슈·분석창고까지 MCP로 훑어 "왜"를 증거로 재구성함. Theo가 "훔쳐가고 싶다"고 꼽은 부분.
  6. 철학의 반대 지점: pstack은 계획 문서를 불신(코드로 계획), Pocock은 grilling+스펙+티켓이 중심. 어느 쪽이 맞는지는 작업 성격에 따라 갈림.

6. 비판·단점·주의점

  • 오버킬 논란: Rob Shocks 실측에서 같은 빌드가 풀 스택 적용 시 약 2배 소요(1시간 vs 30분). "작은 UI 수정엔 토큰·시간 낭비"라는 결론. Theo도 arena 한 번에 수백 달러의 추론 비용이 들 수 있다고 지적.
  • 기존 코드베이스 전제: 계획 스킬이 의도적으로 없어서 그린필드 신규 프로젝트엔 안 맞음(리뷰어 공통 지적).
  • Cursor 종속 요소: 모델 역할 배정, /loop, /add-plugin 등 최상의 경험은 Cursor에서만. 포트는 비공식.
  • 제작자 수치는 자기 보고: "주 1만 회 사용", "월 2,000 PR"은 본인 발표이며 독립 검증 없음.
  • 마찰 포인트: /deslop, control-cli/control-ui는 별도 플러그인(cursor-team-kit), 고급 shipping 플레이북은 GitHub/Graphite 전제.

7. 첫 사용 추천 경로

  1. /add-plugin pstack → /setup-pstack → 새 채팅 시작
  2. 실제 버그 하나에 /poteto-mode <증상>. 먼저 재현하고, 수정하고, 검증해.
  3. 투두에 원칙 읽기 → 플레이북 복사 → 스킬 호출이 보이는지 관찰
  4. /how, /why, /interrogate를 직접 써봄
  5. 익숙해지면 /create-verification-skill로 레포에 검증 능력을 심고, 야간 실행은 완료 조건이 있는 프롬프트 + /loop로
