Ollaya를 Mac mini M4 기본형(10C CPU/10C GPU, 16GB)에서 서비스할 때의 실용성

결론 한 줄: Ollaya는 LLM이 아니라 초소형 "결정 모델" 서빙 런타임이라 M4 16GB에서 핵심 모델은 문제없이 돌아감. 다만 Mac 공식 경로는 CPU(fp32)라 5질문 요청 기준 약 0.4초·초당 2~3 req(추정)이고, GPU 가속은 커뮤니티 MLX/CoreML 포트로 우회해야 함. 24/7 전력·열은 합격. "GPT API처럼 래핑"은 가능하지만 생성 API가 아니라 분류 API이고, 호스팅 Jev 대비 정확도 열위(JevBench 30.3 vs 63.3)가 상품화의 실질 한계임.

0. 전제 정정

Ollaya 자체는 모델이 아니라 Ollama식 런타임(Apache-2.0, Rust 단일 바이너리, 2026-09-23 공개)임. 돌리는 대상은 laya·decider·nli·gliclass·qwen3guard·kev·von 같은 오픈 결정 모델들로, state+typed question을 단일 forward pass로 분류하고 텍스트를 생성하지 않음(출력 토큰 0). LLM 서빙과 부하 특성이 완전히 다름.

1. 16GB에서 돌아가는가

양자화 질문에 대한 답: Ollaya에는 GGUF/int8 양자화가 아직 없음(모델별 fp16/fp32 그래프만; CPU=fp32, CUDA=fp16). GGUF 결정 모델은 planned 상태. Mac에서의 실질 경량 경로는 커뮤니티 포트: laya-mlx(MLX fp16, 피크 1GiB 미만 실측)와 laya-apple(MLX GPU + Neural Engine 혼합).
주의: 공식 플랫폼 표는 macOS를 "CPU only"로 명시. 일부 2차 보도(stackness, samcodeman)는 Mac MLX/Metal 가속을 주장하나 공식 문서와 상충, 미검증임.

동시성·안정성 메모: 서버는 큐잉(OLLAYA_MAX_QUEUE, 503+Retry-After)으로 버스트 흡수, 모델 인스턴스당 추론은 직렬 (API 문서). M4 Max에서도 6분 지속 부하 시 23.5→5.3 q/s 하락 관측(Sperix Labs, stackness 인용). laya-mlx는 장기 상주 시 Metal 메모리 21.7GB 증가 미해결 이슈 — 16GB 장기 운영 시 캐시 제한 필수.

3. 트래픽 관점 (추정)

  • CPU 경로(laya:en, 5질문): 일일 17만~26만 req 이론 상한, 헤드룸 50% 잡으면 일일 약 10만 req 안정권 (추정)
  • 단일질문 경량 요청: 일일 수십만~백만 근접 (추정)
  • MLX 경로 확보 시 상한 일일 백만 단위 (추정, 신뢰도 낮음)
  • 병목 순위: ① CPU 연산(fp32) ② 상주 RAM(동시 모델 수) ③ 지속 올코어 시 스로틀링. 네트워크는 비병목(응답 수 KB → 10 req/s도 업로드 수십 KB/s)
  • 출력 토큰이 0이라 "토큰/초"가 아니라 req/s·질문/s가 지표임

4. 전력·열·24/7 — 매우 적합

  • Apple 공식: idle 4W / max 65W (Apple Support). Geerling 실측 idle 3~4W (링크)
  • 24/7 실측 16일: 열 이벤트 0건, idle 37°C, 10코어 벡터 풀로드 10분에 시스템 ~29W·83.5°C·팬 27%·클럭 유지 (picklog)
  • 지속 인코딩급 부하는 10~15분 후 스로틀링 소유자 보고 (MacRumors) — 추론 서빙은 버스트성이라 해당 낮음
  • 전기요금 (추정): 평균 15~30W → 월 11~22kWh → kWh당 200원 가정 시 월 약 2,200~4,400원 (단가 가정치)

5. GPT API처럼 래핑해 출시 — 구성과 비용

기술 구성

  • Ollaya는 기본 127.0.0.1:11435 바인딩 + OLLAYA_API_KEY 단일 키 → 그대로 공개 불가
  • 구성: Caddy/nginx(TLS) + API 게이트웨이(사용자별 키·레이트리밋·과금). LiteLLM은 /typesafe/v1/systemone 패스스루+비용추적, GoModel은 S1 엔드포인트+가상모델 지원 (stackness)
  • 와이어 포맷이 OpenAI chat/completions가 아니라 TypeSafe /v1/systemone — "GPT 호환" 표방 시 어댑터 자체 제작 필요. 어차피 생성이 아니라 분류/판정 API라 카테고리가 다름
  • 홈 호스팅 공개: Cloudflare Tunnel 등 NAT 우회 + 도메인

비용 구조 (추정)

  • 하드웨어: Mac mini M4 기본형 89만원 (미국 $599) — macmini.co.kr, Apple KR
  • 전기 월 수천원 + 도메인/터널 무료~수천원
  • 대안(호스팅 Jev): $0.042/백만 입력토큰·출력 무료, 3질문 요청 ≈ $0.000019, 100만 건 ≈ $19 (jevaiguide)
  • 손익분기 (추정): 일 10만 req를 Jev로 처리하면 월 ~$57 → 기기값 $650 기준 약 11개월. 일 1만 req면 ~9.5년. 트래픽이 클수록 자체 서빙 유리

품질·라이선스 리스크 (가장 큼)

  • 정확도: JevBench Laya 30.3 vs Jev 63.3 (842 decisions, creativeainews 인용). 기본 laya 체크포인트는 Convai 자체 벤치에서도 다수클래스 베이스라인 밑 (0.362/0.342 vs 0.461, orcarouter) → 자체 데이터 파인튜닝+온도 재보정 사실상 필수
  • 컨텍스트: laya 512~1,024토큰(von 8k) vs Jev 64k. laya:en은 초과 입력을 조용히 절단
  • 라이선스: 런타임·laya·decider·gliclass Apache-2.0 → 상업적 래핑 가능. ¹nli(deberta)는 학습데이터 일부 비상업 조항 → 상용 부적합. "자체 모델"처럼 표시하면 평판 리스크

6. 결론이 뒤집히는 조건

  • Ollaya가 Mac GPU(MLX/Metal)를 공식 지원 → 처리량 수십 배↑, 일일 상한 수십만→수백만
  • decider:2b급 정확도 필요 → 16GB 불가, M4 Pro/Max급 상향
  • 지속 트래픽 초당 수 req 이상 → 1대로 부족
  • 입력 상태가 1,024토큰 초과 빈번 → laya 계열 부적합, von(8k) 또는 Jev
  • Jev 가격 인하 (TypeSafe가 인하 공언) → 손익분기점 더 멀어짐
